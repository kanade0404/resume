# ターゲット職種プロファイル: LLMプロダクト開発職

全ペルソナが、担当IDを当てる前に読む。ルーブリックは職種に中立なので、この職種の読み手が経歴書で探す証跡をここにまとめる。
応募先の職種が変わったら、このファイルを差し替える。

各項目の `[n]` は末尾の参照元に対応する。参照元の無い項目は「推測」と付けた。

## 読み手が探す証跡

### 評価と品質

- 「動いたことをどうやって確かめたか」が書かれているか。LLM職の面接で最も差がつく質問になっている [1][2][3][4][9]
- 評価セットの出所(本番データか合成データか)、件数、合否の基準、変更ごとに評価を回しているか [3][4][5][9]
- 出力のログを実際に読み、失敗を分類して数え、そこから評価項目を決めたか(エラー分析) [6]
- LLM審判(LLM-as-a-Judge)を使った場合、人の判定との一致を確かめたか [6][9]
- 品質問題の原因を、プロンプト・検索・モデル・データのどこにあるか切り分けたか [7]
- モデル更新時の回帰をどう検知するか [9]

### 本番運用

- 本番に出して運用した経験か、PoC・デモ止まりか。PoCのみの経験を対象外とする求人がある [8][10][11]
- 利用者数・呼び出し回数・障害対応・監視など、本番運用を示す材料があるか [3][10]

### トレードオフと設計判断

- 精度・レイテンシ・コストのトレードオフをどう判断したか [3][5][7][12]
- モデルに任せる範囲と、コード・人の確認で保証する範囲をどう線引きしたか [13][14]
- LLMやエージェントを使わないと判断した経験があるか [7]

### 経験の示し方

- 業務の実績と個人開発・検証が区別して書かれているか。個人開発のLLM経験も評価対象になる [13][15][16]
- LLM経験の年数より、Webアプリ開発の基礎(API設計・DB・性能・テスト・監視)と評価設計の理解を重く見る企業がある [15][9]
- AIを前提に自分の仕事の進め方を変えているか [17][18]
- GitHub・技術ブログ・登壇など、外部の成果物と経歴書の記述が一致しているか [19][20]

`[n]` は根拠の番号(一覧は references/sources.md の「target-profile」節。保守用なので、レビューでは読まなくてよい)。
