## 4-1 記事一覧の作成

### note(公式・個人)

note は WebFetch で本文が取れないことが多いため、Playwright の `browser_evaluate` 内で `fetch` して API を叩く。

- 一覧: `https://note.com/api/v2/creators/<urlname>/contents?kind=note&page=N`(`isLastPage` が true になるまで N を増やす)
- 本文: `https://note.com/api/v3/notes/<key>`(`key` は一覧の各記事の `key`)

Playwright のルール(**共有ブラウザ**であることが前提):

- `browser_navigate` は**最初の1回だけ**(`https://note.com/` を開いて同一オリジンにする)。以後は遷移しない
- 並列 subagent は `browser_navigate` 禁止。同じページを共有しているため、誰かが遷移すると他の subagent の処理が壊れる
- リロード・遷移で `window` に置いたキャッシュは消える前提で、取得結果は都度 scratchpad のファイルに書き出す
- 1回の `browser_evaluate` で取る件数を絞り(例: 一覧1ページ、本文5件)、応答が巨大にならないようにする

### RSS / テックブログ / PR TIMES / SpeakerDeck

- RSS は多くの場合**最新50件程度が上限**。それより古い記事はアーカイブページ・サイトマップ・一覧 API で補う
- 一覧に載らない古い記事は「RSS 上限のため未取得」と記録する(無いとは書かない)

### 個人 note・個人ブログ

- **在籍が確認できたもの**(記事内・プロフィールで対象企業の所属が明示)だけ取り込む
- 在籍時期と記事の公開日が重ならないものは「元社員」として発信者区分は「社員」、サマリに在籍時期を書く

### 重複チェック

- URL を正規化(クエリ・末尾スラッシュ・`utm_*` を除去)し、外部発信DB の既存レコードの URL と突き合わせて重複を除く
- 同じ記事が複数媒体に転載されている場合は原典を1件だけ登録し、転載先はサマリに書く

## 4-2 最初のバッチで基準を固める

最初の5〜10件を1つの subagent に処理させ、**main が結果を読んで**次を確認してから残りを並列化する。

- 発信者区分・種別の判定が下の基準どおりか
- サマリが本文全文に基づいているか(冒頭だけの要約になっていないか)
- ポジショントーク注意が「具体的問題がある場合だけ」になっているか

基準の補足・修正があれば `<scratchpad>/42-pub-criteria.md` に書き、残りのバッチの subagent に読ませる。

## 判定基準(固定)

### 本文

- **全文を読む。** 冒頭やリード文だけで要約しない。長い記事は分割取得してでも最後まで読む
- 取得できなかった記事は「本文未取得」と記録し、タイトルだけで要約を書かない

### 発信者区分

| 区分 | 基準 |
|---|---|
| 経営陣 | 代表・取締役・執行役員・CxO が**主たる語り手**(インタビューの回答者、記事の著者) |
| 社員 | 上記以外の在籍者(元社員の在籍時の記事を含む) |
| 公式 | 会社名義・広報名義で、特定個人が主たる語り手ではない |
| 第三者メディア | 外部メディアが取材・執筆した記事で、語り手が特定できない、または複数社の比較記事 |

経営陣が登場する第三者メディアのインタビューは、語り手が経営陣なので「経営陣」にし、媒体を「インタビュー記事」にする。

### ポジショントーク注意

**具体的な問題がある場合だけ**書く。採用記事が前向きなのは当然なので、それだけでは書かない。

| 記号 | 書く条件 |
|---|---|
| (a) | 出典・母数の無い数値、根拠の無い「No.1」「唯一」 |
| (b) | 語り手が出資者・人材紹介会社・取引先など利害関係者 |
| (c) | 施策を肯定しているが成果の数値が無い(「導入して良くなった」だけ) |
| (d) | 他記事と数値が矛盾する(どの記事のどの数値か書く) |

書き方: `(a) 「導入社数No.1」の調査主体・時点の記載なし` のように記号+具体箇所。

### 種別

記事の主題で選ぶ(複数可)。事業 / 開発・技術 / 採用 / カルチャー・組織 / 経営・資金 / プロダクト / イベント。

## 4-4 外部発信DB への登録

- 1記事1レコード。列の意味は `notion-schema.md` の外部発信DB 節
- **企業 relation を必ず設定**する(設定漏れは後から探せなくなる)
- 登録前に URL 重複を再確認する(並列バッチ間で同じ記事を拾っている可能性がある)
- 登録は sonnet subagent に任せてよい。件数が多い場合は 10〜20 件ごとに区切り、main が件数を照合する

## 4-5 記事横断の知見

全バッチの結果から次をまとめ、Phase 5 で企業ページへ差し込む。

- **組織**: 組織変更・役職変遷・採用方針の推移
- **技術**: 技術スタックの変遷、リプレイス、技術的負債への言及
- **事業**: 主力事業・顧客セグメントの変化、撤退した事業
- **投資家論点**: 調達・評価額・IPO への言及、経営陣が強調する指標
- **食い違う数値**: 同じ指標が記事によって違う一覧(記事URL・日付・値)

各知見に出典記事の URL を付ける。
